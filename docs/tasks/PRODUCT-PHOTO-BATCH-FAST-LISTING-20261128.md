# BoBuy 现场照片批量快速上架开发计划

日期为 2026 年 11 月 28 日，日本时间。源码基线为 GitHub `sunshaoxuan/bobuy` 主分支 `eaf31c37`。阶段为已批准，已提交云端开发。

## 1. 目标与范围

商品档案增加「批量快速上架」。运营选定供应商与市场，同批拍照或从相册、电脑多选上传。系统后台逐个识别、收集和校验商品文字资料。每个商品资料正确且齐全后直接公开上架，前台能按货号和商品名找到；无需人工审批、二次确认或等待同批其他商品。缺少正式商品图时，前台显示「图片准备中」。

后台确认整批商品公开可查后，才启动独立的官网找图任务，逐个从供应商官网与品牌官网查找图片。找图结果回到原批次，供运营使用现有商品档案补图。发布权限、售卖规则、库存和现有单件拍照确认流程沿用既有机制。本期交付官网图候选及来源，运营沿用商品档案审核来源、选图和保存；目前计划范围为搜索和候选回传，官网图编辑与自动替换属于后续需求。

## 2. 第一阶段：资料收集与自动上架

1. 商品档案内复用现有现场拍照和文件校验。上传前把多张照片归到对应商品，可给同一商品上传包装和价签等多张照片。批次及商品行在服务端持久化。页面显示按商品计数的总数、处理中、已上架、需补资料、处理失败，刷新后可恢复。重复选择或网络重试返回原记录。图片内容只作商家私有凭证。
2. 识别后用商家、供应商、市场、准确货号及规格核对唯一身份。条码可作交叉校验。同号不同规格、多候选、历史已隐藏或删除、归属不明时，展示具体问题；禁止模糊撞名后自动重建或恢复。已公开的同一商品关联原档案并标记「已在前台」，保留原资料和商品 ID。可以自动上架的已有私有档案须有批次来源归属，且未曾被人工隐藏或下架；其它已有私有档案提示运营处理来源或状态。
3. 上架必需项为可核验的货号、商品名称、规格或包装与销售单位、对应分类及商品介绍，商品品牌在来源有标明时写入。名称、规格、介绍覆盖简体中文、繁体中文、日文、英文。译文源自同一份可核验事实并采用现有字段校验；数量、单位和型号跨语言一致。事实优先以清晰现场包装和与货号及规格一致的可信来源为准。重要字段冲突、缺失、来源无法核验或译文校验失败时，只要求补正相应字段。配料、过敏原、认证及功效等可选事实仅在有来源支持时录入。图片、找图状态和图库 URL 均不参与文字上架判定。
4. 条件满足时，后台在单商品事务内保存完整资料、公开可见性和关联商品 ID。写入后用真实前台目录详情和匹配读取路径核对同一 ID，确认后显示「已上架」及前台链接。若首次回读失败，保留原商品 ID 并重试核对。单项识别或资料错误只影响本项，运营补字段或补拍后重新校验，齐全便自动上架。
5. 网站已有确认售价和符合售卖规则的商品可按现有流程加购结算。本功能允许无确认售价的商品公开展示并参与查找或匹配。该状态显示现有无可用售价反馈，保留现行结算约束。现场采购参考价与 BoBuy 售价分别记录；禁止用零价、猜测价格或现场价生成售价，也禁止从照片推导库存数量。

## 3. 第二阶段：整批上架后查找官网图

1. 已上架和已在前台的行均以真实公开回读为准。所有本批纳入上架的商品均通过回读后，批次状态变为「上架完成」，异步建立逐商品找图任务。有问题的行可以补正；误传或此次确定不做的行可显式移出本批并保留记录，批次统计单列。自动找图以该批剩余且已核对公开的商品为范围。
2. 优先用货号或条码查供应商官网，再查询品牌官网，以型号、规格、包装、销售区域及版本交叉验证。沿用可信来源和安全下载机制，仅使用已验证的官网域名及允许的媒体主机，保存来源页、候选图和匹配依据。图片与商品号和规格无法对应、来源授权不明、网站暂不可用时显示原因，支持逐项重试。已有正式图的商品标记「已有商品图」。
3. 找图任务和上架状态分别持久化。找图失败、超时、重试或部署回滚都不得改变商品可见性。候选图置于商家可见范围，只有运营通过商品档案选图保存后才显示为正式图，前台占位在同一商品 ID 上自动消失。原批次提供「找到候选」「未找到」「已有商品图」和商品档案入口。
4. 正式图来源确认沿用图库现有流程。本计划中的商品上架无需审批，官网找图和选图发生在商品已经公开之后。

## 4. 云端实施顺序

1. 基线核对及拆分。现有 `CostcoOnboardingController` 已支持私有单图任务，`CostcoOnboardingWorker` 已处理可恢复的异步队列。`ProductPhotoIntakeService.confirm` 是现行人工确认入口，`ManualProductCreationService.createPhoto` 当前写入 `DRAFTER_ONLY`。`PublicProductCatalogService` 和 `PublicProductBrowseService` 读取公开档案并可按货号、名称等字段匹配；`StorefrontService` 另按有效卖价读取可售商品。新增快速上架入口，沿用领域校验、分类、权限及来源能力。复核前台匹配的生产版本及购物车请购入口的部署状态，有入口就覆盖，没有入口时记录独立依赖。
2. 先实现最小闭环。上传一批至少两个商品，从持久化到无图公开、匿名查询及批次回读，再增加补资料、冲突、重试和权限检查。沿用现有数据库和队列；确需新字段或记录时使用版本化、可重复安全执行、与旧应用兼容的增量迁移。按商品做并发领用和幂等声明，重新检查权限和身份，保护商家已有档案。
3. 接通整批公开后的找图队列、官方候选结果和既有图上传入口。可借用成熟异步批处理的逐项执行与逐项回执模式；以 BoBuy 当前队列和技术栈实现。参考 [Shopify 批量导入设计](https://shopify.dev/docs/apps/build/apis/graphql-admin/bulk-operations/imports)。
4. 云端提交 PR 前记录实际变更路径、直接消费者、最小检查、预计耗时和停止条件。跑定向测试与真实浏览器验收，交 PR 原生门禁完成其负责的检查。云端回传提交 SHA、相关用例、截图、迁移验证、实际 AI 与官网联通结果、回退方案及生产依赖。照片识别配置需在目标环境用真实照片请求核对。现有基础 Compose 的照片 worker 默认关闭，生产叠加文件配置为默认开启，历史照片验收曾出现模型未配置，不能作为当前生产配置结论。复用有授权的配置入口，不向云端交接凭证。

## 5. 开发验收与生产验收

1. 混合批次测试。两种新商品中一项文字首先齐全，该项无需操作立即公开，按货号、各语言名称查询命中对应详情。另一项缺规格，显示缺项，补正即自动公开。同批已有商品关联原 ID。核对全批自动计算状态、刷新、重新登录、短时断网、重复上传与两端并发，确保无重建、无跨商家访问。
2. 前台及价格。匿名查看缺图商品卡和详情，确认「图片准备中」无破图、无私有原图泄漏，售价缺失时按既有规则限制加购结算，有效售价路径正常。验收相关已有购买匹配入口，覆盖独立发布的依赖状态。检查四种语言和适用最窄支持视口。
3. 找图顺序及失败。最后一个有效商品公开前没有后台官网找图请求。全部公开后任务逐项启动，使用至少一个供应商官网及一个品牌官网的实际样例验证来源与型号规格。错误包装、同名异款及非官网来源不得进入候选。无结果或超时后商品仍能查到；从批次打开商品档案，补图保存后原 ID 展示正式图。
4. 视觉及功能证据。使用现有组件规范，开发前按控件角色记录适用视口及状态的间距、字形和热区预算。默认按钮字形四边至少 3px、实际居中偏差不超过 2px 或字形高度的 10% 两者较小值、相邻热区至少 6px、手机主要热区至少 44px。在真实运行环境覆盖 360px、390px、1280px 和最长译文，提交整体截图与变更区域原尺寸图，分开记录交互、Console、网络、几何与视觉。按项目规则用合规 Gemini 对照实际截图并由主 Agent 复核。
5. 生产交付顺序。用户批准计划后由云端开发。云端定向验收和原生门禁通过后，协调者按既有发布流程绑定候选、迁移、生产模型和官网连接条件及回滚，直接发布。发布后由协调者使用现有隔离或受控验收数据在生产核对版本、真实照片入队、自动公开查询、批次找图和正式图替换，回收临时验收数据并汇报实测。测试只用授权测试范围，避免真实顾客下单或改写既有商品。回退优先关闭新增入口及工作任务、恢复兼容应用，保留已有商品和写入记录，按商品回顾异常。发布和本地验收分别记录版本、结果及任何缺证据项。

本计划以商品公开、前台匹配、独立找图、正式图补齐和生产验收全部完成为交付标准。
