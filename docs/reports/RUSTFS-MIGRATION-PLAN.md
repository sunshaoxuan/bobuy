## Real code paths and contracts

- `bb_recommendation_image` stores ID, merchant ID, existing image_hash, content_type, access_scope and non-null bytea content. Existing hash semantics differ for shared product uploads versus scope-prefixed private uploads; **do not overwrite image_hash or dedup identities**. Migration uses a separate raw content SHA256.
- Recommendation registration/gallery and product-master upload write image rows directly in RecommendationService/ProductCatalogService. `ImageStorageService` handles AI onboarding evidence, procurement receipts, expense vouchers and thumbnail references. All these insertion paths must use the same new binary abstraction/outbox; changing only ImageStorageService would miss the566 current photographs.
- Public route `/api/storefront/recommendation-images/{id}` checks PUBLIC scope and deleted-product references in RecommendationService before returning bytes, Content-Type, nosniff, inline disposition and30-day public immutable cache. Private `/api/merchant/media/{id}` checks PRIVATE scope plus current merchant ownership and returns no-store. Preserve these application URLs, permission checks and cache boundaries; do not redirect private media to publicly readable objects.
- Existing controllers return complete byte arrays, with no explicit Range implementation. Current thumbnails are existing stored assets, not a separate image transformation service. Range/conditional/multipart compatibility must be tested against pinned RustFS and deliberately handled by the application proxy; no current Range pass is claimed.
- Old MinIO service performed bucket creation, public read/list policy, putObject and1-hour presigned GET, using the MinIO SDK. Its public policy and fail-open/null-return behavior must not be revived. No MinIO SDK/config remains in the current application dependency/compose files. Use a maintained S3 client abstraction, not a restored vendor-specific MinIO subsystem.

## Minimal implementation batch (pending)

1. Add disabled-by-default binary storage adapter and additive image-location/outbox structure; keep PG bytea non-null and authoritative during migration/rollback. Keep metadata, ownership, logical-delete relations, galleries, media IDs and public/private URLs in PG. All image insertion paths enqueue the raw hash/length/content type transactionally with PG storage; do not re-import products.
2. Use a private Bobuy-only bucket, stable immutable keys such as `media/v1/{merchantId}/{scope}/{imageId}/{rawSha256}`. Application authorization precedes fetch. Server-side worker uses a scoped application identity, never RustFS root. No anonymous list/read or public bucket; no browser access to S3/admin ports or credentials.
3. Backfill from a consistent PG inventory. Lease/checkpoint jobs, immutable keys and content hash make retries/response-loss idempotent. Verify uploaded objects with HEAD metadata plus GET/raw SHA256 and exact length/content type; ETag alone is insufficient. Only verified matching versions become readable object locations. Preserve failed/pending jobs and PG fallback. Abort corruption/conflicts; never mark mismatches complete.
4. Concurrent new writes commit PG plus outbox in the same transaction. Resume workers safely across restarts; process incremental jobs until no lag. Final reconciliation compares every source row with verified target, totals, bytes and ordered ID/raw-hash manifest. A short approved write freeze is the final boundary, not the entire transfer. Do not rely on UUID sorting or a one-time count to detect new writes.
5. After exact-version synthetic tests and a fresh recoverable backup/restore rehearsal, copy the existing566 (and any legitimate later additions), retaining all PG bytes and deleted-item evidence. Switch preferred reads to RustFS only after final reconciliation, preserving PG fallback. New writes continue PG+outbox throughout the rollback window. Restore PG-preferred reads on failure, so post-cutover uploads are not lost. Never roll back to an application that ignores logical deletion. No PG byte cleanup is authorized in this batch.
