## Production window proposal: approval still required

Allow **5 minutes expected, reserve10 minutes** of API maintenance/write freeze. This estimate uses the measured17.24-second source backup and7.09-second real restore, with remaining time for five application services, hashes and public/UI health checks. Prepare and verify application images, exact PostgreSQL18.6 digest, old-image recovery archive and Compose rollback configuration before the window; CI must be green for the exact candidate. Production timing may differ from local rehearsal.

1. Enter API maintenance, stop all application writers, and verify no other database writers. Take a **fresh** consistent15.19 backup and exact pre-cutover metadata; do not reuse the rehearsal snapshot as the final source. Archive the retired MinIO directory/configuration before removing its service; never delete its volume.
2. Replace only Bobuy's PostgreSQL service with the pinned18.6 image and a **separate** `data/postgres18` directory. Restore the fresh database and original roles/credentials, compare data and metadata, and retain `data/postgres` untouched. Apply V18/V19 with the accepted artifact and compare every preexisting column; only new schema/defaults and migration history may differ. V18 remains inactive: no encryption key, SMTP credential or mail enablement is supplied.
3. Start application services and check actual PostgreSQL version/digest, running application commit, API readiness, public recommendation images/content, normal authorization failures and administrative page. Reopen writes only after all checks pass. No business content, sales price, stock, registration or purchasing state is changed.
4. On failure **before writes reopen**, stop new writers, restore prior Compose/application configuration and PostgreSQL15 against the unchanged old directory; verify health and preserved data before reopening. If any write has reached18, keep maintenance and reconcile it rather than blindly returning to a stale15 directory. Missing/changed rows, image hashes, permissions, constraints, migration failures or unhealthy business APIs trigger rollback.
5. After successful cutover and acceptance, remove the retired MinIO container without `-v`. Inventory exact old PostgreSQL/MinIO image IDs and all running/stopped references; remove only project-exclusive, unreferenced old images after confirming a recoverable registry digest or saved archive. No force/prune, shared-image removal, or deletion of rollback directories/backups.

The ordinary publisher does not orchestrate a PostgreSQL major upgrade; changing its image setting alone is insufficient. A guarded cutover command sequence must be bound to the final candidate and freshly verified source/target configuration before activation. **No production cutover, retired-image removal, mail activation or new secret has been executed.**
