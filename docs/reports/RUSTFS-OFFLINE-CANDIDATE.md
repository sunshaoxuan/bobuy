## Implemented candidate

- `RustFsObjectStore`: disabled by default; explicit file credentials only, HTTPS required, SDK-specific optional CA trust (hostname verification unchanged), bounded requests, PNG/JPEG Content-Type/raw-hash metadata, simple/multipart PUT with abort on failure, HEAD/GET metadata checks and max-size guard. No create bucket/IAM/ACL/delete operation. It exposes no browser object URLs or client hash lookup.
- `MediaBinaryService`: all five current image insertion entry points now preserve validated PG bytes and enqueue transfer metadata in the same database transaction. Existing image IDs, dedup semantics, ownership and URLs remain unchanged. Scope-specific media identities remain independent even when bytes share one physical object. Public/private controllers authorize first, then invoke optional object-preferred read; missing/corrupt objects fall back to retained PG bytes without logging provider exception/secret text. Preferred object reads default false.
- Physical keys are **raw-byte SHA256 content addressed**, `blobs/v1/sha256/{first2}/{sha256}`. Server computes the digest; no client digest is trusted. Shared blob metadata validates length/type and compares retained source bytes before binding another reference. Existing matching objects are GET/hash verified and reused; incompatible existing object content is not blindly overwritten. Different thumbnail bytes create different objects.
- Explicit `bb_media_reference` maps each stable media identity to `bb_media_blob`. Existing business gallery/receipt/source URLs remain the source of their stable media ID relationships; the media record itself is a conservative retention root until permanent retirement. A product/recommendation's logical deletion **never removes that root**. This intentionally retains orphan media records too: no automatic real-business unlink or image-retirement endpoint was introduced.
- Additive V21 defines catalog guard/blob/reference/outbox tables only; PG content remains non-null and is not cleared. A database guard serializes new bindings, claims, completions and GC review. Leases and immutable keys tolerate retries/response loss; stale lease completions cannot win. New inserts below a backfill cursor still enqueue transactionally. Workers recheck source state before verification, preventing a changed source from accepting an old copy.
- GC is **audit-only**: no delete implementation, no deletion grant. No-reference blobs require no remaining PG media row, no transfer row, expired in-flight hold and a24-hour candidate delay; review repeats those checks under the same guard. New references cancel a candidate. Existing rows/active migration hold conservatively prevent collection even if a reference row were damaged. This is not a durable deletion permit; a future destructive GC execution protocol requires its own approval/design and race barrier.
- No scheduler/startup backfill/public migration endpoint exists. Methods are internal preparation primitives, not an activated background pipeline. A formal resumable operator orchestration/reconciliation report, real S3 Range/conditional behavior, exact PostgreSQL V21 migration/restore and browser acceptance remain pending.
