# Recommendation item publication

Goods issues now publish one reviewed occurrence at a time. New associations start `PENDING`, including additions to a published issue. First-item publication activates the existing issue with its publisher/time; other pending associations remain stored and private. Existing public items stay online while an eighth item is appended to seven public items. Service articles retain their existing whole-article workflow. The old goods whole-issue button cannot promote pending items.

`POST /api/merchant/recommendations/{postId}/items/{itemId}/publish` accepts only `{requestId, version, productVersion, sourceHash, reviewed:true}`. Authentication fixes the merchant. The existing merchant user lock serializes writers; the selected master is pessimistically locked, and post version, exact master version and a deterministic hash of original issue facts plus full current catalog metadata/media must match. The source hash is returned only in the merchant detail as `publicationReviewHash`, with `publicationProductVersion`. Identical committed request replay returns current detail; changed replay or stale versions/evidence returns 409. Append intent hashes also retain all submitted facts and the selected version, so a lost response can be retried after the master changes without adding or overwriting a second association.

Publication records a detached snapshot of the occurrence’s stored facts and exact reviewed master metadata. Public reads apply that snapshot rather than the current master. A later 47506 correction therefore cannot rewrite an earlier public issue’s specification, gallery, quote, channel or source. Pending editors cannot change or delete published occurrences. An already-linked catalog no-op remains a no-write idempotent response. No product visibility, selling price, stock, order or payment state is changed by publication.

V31 adds state, immutable publication content, source/version/request bindings and indexes. It does not depend on C3 V29 or R13 V30. Migration preserves original columns, associations, galleries, quote history and source context. For legacy published issues, historical master binding is **unknown**: the snapshot uses only already-stored item facts/translations/gallery/context, `legacy=true`, `catalog=null`, and null product version/product source hash/review hash. It never borrows a current recipe or labels today’s record version as a historical review. Draft issues remain pending. Merchant/public DTOs expose `publicationLegacy=true` and null version for this unknown legacy binding. This intentionally prevents the former floating-master projection from rewriting old issue facts; a new explicit publication uses the reviewed current version.

Read-path audit: `RecommendationService` supplies filtered detail/feed/browse/node/cover data; `RecommendationTaxonomyService` is the shared item filter and frozen projection; `PublicProductCatalogService` uses that projection before reference-only eligibility/counting; product browse/markers derive their visible dataset from that catalog; recommendation paging/search/categories/directory/links derive from `publicBrowseEntries`. `ReferenceQuoteService` separately filters and snapshots its repository candidates so pending prices cannot alter public conflict/unknown-window counts. The native recommendation query in `ProductLifecycleService` is an internal recovery-association read, not a public disclosure gate. Existing image storage and source asset identities are retained.
