## Delivered behavior

The customer's order page now opens a real `GET /api/customer/orders/{orderId}/amendment` view and submits `PATCH` to that same authenticated customer route. The server resolves the actor through existing AuthService, locks and refreshes the current user, verifies the current CUSTOMER role, and fixes every lookup/write to that user's own order. The body cannot provide customer/merchant identity, roles, status, payment, fulfillment, prices or verification state.

Only own NEW + UNPAID orders on a currently bookable trip can change, with no purchased quantities, picking, receipt/billing, reviewed receipt allocation or payment-ledger commitments. Confirmation/paid/refunded/fulfilled/frozen orders remain read-only and direct the customer to the merchant. Unsupported ambiguous legacy line identities fail closed. The form supports product addition/removal, quantities, and an explicit complete replacement of this order's address snapshot. Omitted delivery retains the order address. It does not update the customer's profile, cancel the order, confirm procurement, or perform payment/refund operations.

String product IDs retain the existing nonblank/max-255 contract, including UUID and legacy String IDs. Strict JSON readers reject numeric product IDs and fractional quantities. Products are rechecked under sorted product locks against the existing PUBLIC/merchant and ProductSaleService policies. All requested quote tokens/revisions/currencies must still match at one pricing instant after locks; no client price is trusted. Current amounts and sale units are visible before save. Names/brand/ITEM/model/packaging/specification remain separate business facts. Unavailable items retain their original order snapshot labels and require explicit removal/replacement.

## Revision, idempotency and writer consistency

The common lock order is user (customer command), sorted trips, fresh order rows, then sorted products. OrderWriteCoordinator refreshes after waiting for a lock to avoid stale authorization/persistence-context entities. Repeated calls retain changes already made under that transaction's trip lock. Inventory reconciliation no longer locks all NEW orders before obtaining its target trip lock; it selects scope, locks the target trip and rereads/locks its orders. Merchant upsert/quick-order/status/delete/bulk, procurement/receipt/billing/picking, trip updates/workflow and checkout use the compatible trip boundary. No other non-test order repository writers were found in the project scan. Seed/reset facilities were not invoked.

OrderHeader gains an optimistic `order_revision`. Full merchant replacement must supply `expectedOrderRevision` for customer-owned orders; the API wrapper sends the revision obtained from the server. Stale replacements conflict rather than overwriting customer edits. A missing payment state inherits the current state. The customer command never uses this generic replacement path. Status commands reread current line data under the shared lock, preserving a preceding customer edit. Lock/serialization conflicts return HTTP409.

The customer revision is a deterministic SHA256 of the authoritative order/version and relevant trip state. Payload fingerprints separately bind actor, order, expected revision, canonical String lines/quotes and explicit address intent. The user lock serializes a customer's request UUID namespace. V29 adds an immutable private receipt containing actor, request, order, payload hash, pre-edit order and accepted result in the same transaction as the order change. Database uniqueness protects the per-customer request key. Identical replay performs no order write; a changed payload with the same key conflicts.

Current ownership and trip/order locks are checked **before** receipt replay. An old owner cannot retrieve a receipt result after reassignment. The same current owner can replay after later confirmation/payment without applying a new edit. Such a replay returns the historical accepted result, not current edit permission: the actual UI always performs bounded fresh view/list reads before presenting success. Failure of those reads retains draft and request key; the UI does not announce success. A fresh PAID/locked view wins over an editable replay response.

The form keeps drafts on conflict, uses explicit fresh reload, reuses an unchanged uncertain request key, and protects account/session/order changes, unmount, newer incoming views and late replies. Four-language customer text is complete. No management entry is added to the customer page.
