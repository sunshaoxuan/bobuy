# RustFS production activation boundary — preparation, not activation

This supersedes the rollback and writer-credential assumptions in the initial proposal. Production is unchanged. Previous live PG15/operator and RustFS test evidence remains in `RUSTFS-OPERATOR-PG15-ACCEPTANCE.md`; new code is not covered by those old results.

## Bounded delivery

1. V21 holds shared raw SHA-256 objects, explicit retention references, serialized holds and durable transfer leases. Logical deletion preserves references. Garbage collection remains audit-only; there is no object deletion operation.
2. Additive V22 permits object-only new media and backfills raw hash/length for existing PG bytes. It does **not** clear or delete any existing binary. IDs, business URLs, owners and access scopes stay stable.
3. Default-off `bobbuy.media.worker.enabled`, together with enabled RustFS, activates a single bounded worker: 5-second delay, up to 10 transfers/cycle, no overlapping cycles or startup business scan. Transfer leases expire after 120 seconds; failure retries after 30 seconds. Process loss can repeat verification, not create a new key. Generic logs contain no external exception text or credentials.
4. Separate default-off `bobbuy.media.object-only-writes` requires object reads and enabled storage. New bytes are server-hashed, written and read back under the catalog guard before the PG metadata/reference transaction commits. A failed store returns 503 without committing an unusable image; a lost response can safely retry the same content key. Transaction rollback may leave a harmless retained orphan, never a premature deletion. Existing PG copies remain present even when an existing upload is reused. Object-only uploads never silently fall back to writing PG binaries.
5. Audit/checkpoint verification supports retained-PG and object-only records, independently checks actual objects and reports PG retained rows/bytes versus object-only rows. Missing/corrupt object-only images fail closed; they cannot be reconstructed from a PG metadata backup alone.

## Ordered activation and rollback

1. Freeze the final candidate; affected gates and PG15 V22 restore must pass. Bind exact application images/CI. Create production security assets only after the explicit package above is approved.
2. Coordinate a write freeze for **all binary writers, including AI**, apply V21/V22 and start the compatible applications with object-only writes and object preferred reads **off**. V22's required raw metadata columns are not writable by an un-upgraded image inserter: do not run old binary writers during this rollout or claim a rolling zero-freeze upgrade. Existing PG bytes are preserved, but schema data preservation is distinct from old-writer compatibility. Upgrade every binary writer to transactional outbox support before reopening writes and online copying. Start only the approved transfer worker; verify retained PG fallback. Old PG bytes remain the migration authority.
3. Run bounded resumable full copy plus incremental drain; compare every object hash/type/length, explicit references, counts and aggregate fingerprint. Brief final write coordination/read switch is separately approved after timed rehearsal; preparation duration is not downtime.
4. Only after an actual object-data backup/restore test and approved durable recovery destination may all writers switch to object-only new uploads. Confirm database rows contain NULL binary plus valid hash/length, while old PG binaries remain unchanged. Do not allow mixed un-upgraded writers.
5. Before object-only activation, rollback can disable worker/read preference and use retained PG. **After object-only uploads exist, simply disabling RustFS or reverting to a pre-V22 application is unsafe.** Keep compatible code; disable new writes if storage fails; old media can read PG, new media requires RustFS restoration. Restore object bytes from the verified object backup and recheck hashes before reopening uploads. Never announce full rollback from a PG-only backup.
6. No old PG binary cleanup, object garbage collection, bucket deletion, PG18 upgrade, SMTP, sales/registration activation, real content update or post3 file permission is included.

## TLS rotation design only

Inventory expiration and alert in advance. Leaf renewal under the same CA needs a separately approved fresh key, restricted-file persistence and atomic cert/key replacement; validate SAN/chain/expiry before a controlled RustFS restart, keeping the previous leaf files for immediate rollback. CA rotation needs approved new keys plus a temporary SDK bundle containing old and new CA, application rollout first, then leaf change and validation, then later old-CA removal. Never disable hostname/expiry verification or expand global trust. This turn does not generate rotation keys or rehearse a new trust configuration.
