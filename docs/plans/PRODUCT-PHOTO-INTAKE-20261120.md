## 1. 用户目标与现状

运营在「商品档案管理」拍照或上传一张现场图，系统调用 AI 识别并查找商品。已有商品检查和更新照片对应的价格，并确认「有货」。新商品用 AI 补齐档案，用户核对后创建。截图中要求关闭弹窗去「Costco AI 录入」选择供应商的提示是现状证据。

源码核对：

- `frontend/src/pages/StockMaster.tsx` 的桌面和手机拍照按钮将弹窗交给 `frontend/src/components/CostcoOnboardingPanel.tsx`。供应商在弹窗外，照片提交还依赖后台 worker 可用。当前 `AiQuickAddModal.tsx` 的 durable 分支只有提交任务，缺少就地完成查货和确认保存的反馈。
- `backend/src/main/java/com/bobbuy/api/CostcoOnboardingController.java` 与 `CostcoNumberOnboardingService` 为照片和货号提供可追踪任务。其 `CostcoCatalogCommitter` 对符合身份与准入条件的已有档案执行资料补全。没有匹配时进入 `onboarding.new_master_needs_price_policy`。参考价格在候选中，现场观察没有可确认的写入步骤。
- `ManualProductCreationService` 已提供私有商品创建。用它或同一领域入口保存新商品。旧 `AiAgentController` 确认流程可写 `basePrice`，新建分支可能使用 0 兜底，不能直接用作新流程的落库入口。
- `ProductPricingService` 的常规价格用于经营售卖管理，并有审核与版本要求。`MerchantSku` 虽有 `lastPrice` 和 `StockStatus`，本次核对只找到这两个字段的模型 getter 和种子用法。实施前验证语义、所有权、唯一性和真实消费者，不能仅凭字段名选作写入目标。

## 2. 用户操作

1. 在商品档案点「拍照识别商品」。弹窗内直接提供设备拍照和相册或文件上传。桌面可上传，手机走原生后摄选择能力并保留相册入口。文案说明把商品、货号和价签尽量拍在同一张图里。照片替换与取消在原处完成。
2. 只有一个可用供应商时可预选，多供应商时在同一弹窗选择。显示加载失败或无可用供应商的具体原因。照片预览后点「识别并查找」，显示已接收、识别中、待确认或失败。异步任务从商品档案可重新打开结果，刷新页面可恢复同一任务。AI 挂了、图片格式不支持、网断或识别失败时保留已确认的输入并给出明确重试动作。
3. 唯一匹配时，展示商品名、货号、供应商、规格与照片证据，同时对比最近已确认现场价与本次识别价。显示价格单位、币种及是否存在促销条件。运营核对并可更正价格，明确确认「现场有货」后保存。价格相同显示「价格未变」，仍允许确认有货。保存完显示实际写入结果并刷新商品档案，重开可查到新价格和标记。
4. 无匹配时，打开预填的新商品表单。识别、查找和补齐由系统完成，无需输入 AI 指令。AI 优先从现场图提取，缺项在已支持的来源查找链路内按明确商品身份补齐。将原图及可追溯依据和建议字段一同展示。用户只需核对、更正与填必填缺项，再创建私有商品档案。创建成功后打开该记录并显示本次已确认的现场价格或有货观察。
5. 货号不可读、规格冲突、打包单位不同、同名多件、多张价签或归属不明时，列候选或要求更正货号、选择商品、重拍。已删除的相同身份只提示检查档案或使用既有恢复流程。换图、切换供应商、换账号后丢弃旧识别结果，禁止旧请求返回覆盖新结果。

## 3. 字段与写入规则

| 项目 | 要求 |
| --- | --- |
| 商品身份 | 在当前运营所属商家范围内，按供应商、市场、货号查找，并核对规格、容量及销售单位。有效条码可辅助校验。名称、模糊匹配或 AI 自报 ID 只可作候选。由后端判定存在、无匹配或待确认。历史记录缺供应商或市场时出候选，不自动认为无匹配。创建、确认时服务端重新核验身份和权限，防止并发重复创建。 |
| 新品资料 | 复用当前商品表单的必填规则与现行分类树。预填可核实的货号、名称及四语名称或译文、品牌、型号、规格、包装、单位、分类、说明、可合法使用的商品图片、适用的已有分类属性。字段标明照片可见、可靠来源、AI 建议或待补。来源无法确认的值留空，分类允许人工修正。营养、过敏原等事实须有来源。现场价签图作私有证据，正式商品图沿用既有媒体校验。 |
| 价格 | 「更新价格」在本功能默认为照片所证实的现场采购参考价，展示最近值、确认值和差额，保留同一商家、供应商、市场及已确认的金额、币种、单位、观察时间、来源与促销限定。保留可查的价格变化和操作记录。官网网购价、原价、折扣额与现场成交标签分别识别。币种、单包/箱、按重计价、折扣或对应价签含糊时，要求人工确认。金额须符合现有币种精度及字段约束。当前 BoBuy 售价只能经原有售卖调价流程按其权限及版本规则确认，本入口不以采购价覆盖售价。 |
| 有货标记 | 在商品档案显示「现场有货」及观察时间，范围限此次确认的供应商和市场。允许在人工确认证据后只保存有货而暂不更新价格，价格缺失明确显示「价格未更新」。有价签但无商品实物时默认不勾选，允许运营依据现场所见主动确认。无依据保持原状；不增加可售库存数量、不改变预订方式，也不移除无关标签。 |
| 权限与持久化 | 识别阶段只产生私有任务和建议，在运营点击确认前禁止自动更新现有商品档案。照片入口若复用耐久任务，照片请求必须有明确的待确认分支，货号入口沿用现有契约。沿用 AGENT、商家归属、照片私有访问、文件大小/类型校验及配额控制。已有商品的价格和有货同时确认时原子提交。保存按请求幂等，重复点击/刷新/重试不得重复记价、串产品或重复新建。冲突提示重读并重新确认，保存失败可保留待确认输入。 |

## 4. 实现计划与范围

1. 云端核对基线、现有 UI 与接口、AI 图片模型路径和现场价格与有货的可写契约，记录计划修改的路径、直接消费者、预估耗时和最小验证集。高级编码及视觉按本地项目交接的模型规则和环境实际能力处理，凭证不随任务传输。
2. 先跑通现有档案的最小闭环：弹窗上传、识别、查找、确认、重新读取。复用现行 Ant Design、认证、I18n、图片处理、AI 能力或异步任务。若现有现场价格/状态模型不适配，说明理由，在商家范围内选最小持久化方案。结构变更仅用版本化、幂等、旧应用可兼容的迁移；禁止批量改写既有业务数据。
3. 接通无匹配分支的 AI 候选和现有私有创建入口，再覆盖候选、失败、重开和重复提交。优先做单张照片、单个商品的完整路径。本站公开套餐、商品发布、订单与结算、推荐文章、邮件、库存数量、独立调价后台与新的 AI 设置页不在范围内。
4. 冻结候选并运行一次受影响的单元测试及必要集成检查。完成真实浏览器验证后提交 PR，附候选 SHA、测试命令和数量、浏览器/视觉证据、实际 AI 联通结果或具体缺项、数据迁移与应用回滚说明。遵从原生提交及 CI 门禁。云端将候选交给协调者，由协调者处理接入生产发布与线上验收，避免双人同时切换生产。
