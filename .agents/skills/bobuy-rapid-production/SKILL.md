# Bobuy rapid production delivery

Use the existing task, checkout and release operator. This project-local workflow does not grant deployment credentials, security changes or new permissions.

1. Establish the active production revision, candidate diff and current authorization. Separate unrelated dirty files and independently shippable work. One coordinator owns shared browser, container replacement and deployment; reuse the existing Bobuy local stack.
2. Reuse passed evidence when relevant source, dependencies, configuration and data inputs match. Run only checks affected by subsequent changes, plus required CI. Bind UI acceptance to actual loaded asset/JAR hashes. Select desktop/mobile and interactions according to the changed behavior; save/reload and repeat-operation checks matter when persistence or workflows change.
3. For product identity, prices, images, orders or migrations, preserve distinct ITEM identities, associations and history. Verify migration/recovery and old-application compatibility where affected. Unknown business facts stay unknown. Do not release changes known to introduce incorrect customer-facing business data, break critical flows, lose data or prevent recovery; split unrelated safe changes where possible.
4. Resolve observed problems locally and finish the bounded required checks before deciding to release. Prepare the production baseline, exact artifacts, operator and recovery in that phase: read [the existing deployment reference](../../../docs/production-deployment.md) with its date boundary and inspect the actual version-pinned operator and receipts. Once the candidate is accepted and release is decided, execute that prepared scoped release without another routine chat approval. Do not add review layers, insurance checks, repeated valid tests, scope expansion or incidental optimization after the decision. Keep the project's mandatory checks and the actual identity/health/business acceptance and data-protection safeguards. A concrete deployment blocker permits the smallest repair and affected verification; it does not restart unrelated passed checks or an entire delivery cycle.
5. Pin exact commit, artifact/image digests, current production base and executable recovery. For small independent additions limited to reference tables, seed data and read/selection interfaces, use versioned idempotent SQL/scripts, preserve existing business data and verify old-application compatibility. The user authorizes direct production delivery after affected tests and mandatory gates pass, followed by actual production acceptance. Reuse existing offsite streaming backups; verify their coverage/recovery location from available operational evidence and record unknowns. This path has no default extra full snapshot, global writer pause or whole-business-table aggregate fingerprint. Validate source, counts, unique codes, parent relationships and repeated execution with focused checks. Preserve protected services and rollback artifacts. Sequentially activate only scoped services, then check production revision/digests, health, real pages and affected critical flows. Use only authorized synthetic tests; do not create customer orders for verification.
   For business-data rewrites/deletions, destructive schema changes, incompatible old applications, actual locking conflicts or recovery gaps, assess the specific backup/maintenance requirement and document its reason and smallest scope. A schema version increment alone does not select the full-snapshot/stopped-writer path. Existing historical operator templates must be reviewed against this boundary before execution.
6. Before writers reopen, recovery may use the verified stopped-writer snapshot under its operator guards. After actual or uncertain reopening, never restore an old database over new customer writes: contain, inspect and use compatible application rollback or forward recovery.
   For additive reference imports, prefer compatible application rollback retaining the new table, or forward repair. This rule does not require stopping writers for that path.
7. Default sandbox failure is not formal denial; an authorized command may use its native controlled review. For explicit denial, respect its exact scope, do not change endpoint/credentials/tool to bypass it, and retry only under applicable new-evidence rules. Inspect uncertain outcomes before any repeat. Continue independent work while a dependency is blocked.

8. Before handoff, preserve formal deliverables and acceptance evidence, then clean only identified task-owned temporary outputs. For Windows batches or a scoped retry after denial, use the existing powershell-script-preflight skill and its references/task-temporary-cleanup.md workflow. Preserve required release/recovery copies, shared dependencies and other worktrees; record removed and retained outputs. Cleanup uses related integrity/static checks, without repeated business validation or a new release gate.

Current reusable release mechanics: [production publisher and recovery guards](../../../scripts/publish-production.py), [reference-data execution contract](../../../docs/reference-data-release.md), [release guard tests](../../../scripts/test_publish_production.py), and [current test matrix](../../../docs/reports/TEST-MATRIX-本地与CI执行矩阵.md). The publisher requires an explicit mode; reference imports use --mode reference-data with a reviewed hash-bound plan. Maintenance requires a concrete --maintenance-reason and a risk that needs that path. The old full server window is retired and only supports read-only -PrecheckOnly. Deleted ci.yml jobs and historical schema-specific artifact capture lists do not add gates to new tasks. Reuse valid input-bound results and run affected checks once per batch. Check installed script hashes before execution; do not use a historical operator as an implicit shortcut. Match the actual service layout before invoking them. The release-specific operator under .task-tmp/recommendation-20261101-final is a historical reference, not a generic command or current authorization.

Report shipped behavior, production version/time and actual verification. Distinguish built, locally accepted, staged and deployed. For blockers record action, target, reason, execution state and the smallest next step. Keep a handoff receipt so a resumed task reconciles existing actions rather than repeating them.
